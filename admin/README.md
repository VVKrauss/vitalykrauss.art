# Vitaly Krauss Studio

Закрытая серверная часть админки. В этом этапе реализованы вход владельца, сессии, ключи доступа (passkey), смена пароля и восстановление доступа. Редактирование каталога и публикация работ — следующий этап.

Публичный сайт остаётся на GitHub Pages. Содержимое `admin/` не входит в публикуемый архив Pages. Для студии нужен отдельный постоянно работающий процесс Node.js и постоянный диск для SQLite.

## Локальный запуск

Node.js 22.13 или новее. В Node 22 встроенная SQLite выводит предупреждение об экспериментальном API; тесты проверяются на установленной Node 22.20. Зависимости закреплены в lock-файле.

В терминале из папки `admin`:

```powershell
npm ci
npm run setup
npm run build
npm start
```

`setup` создаст локальный `.env` со случайным секретом и попросит дважды ввести пароль владельца. Ввод скрыт. Пароль не выводится и не сохраняется в `.env`; в базе хранится его хеш Better Auth. Владелец по умолчанию: `kraussvitaliy@gmail.com`.

Откройте `http://localhost:4174`. Используйте именно этот адрес, а не `127.0.0.1`: проверяется канонический Host, а passkeys привязаны к домену.

После входа по паролю можно добавить passkey и далее входить с отпечатком, Face ID, Windows Hello или ключом безопасности. Совместимость конкретного устройства зависит от его браузера и системы. Публичная регистрация отсутствует и запрещена на сервере.

`.env`, `.data/`, базы и собранный клиент исключены из Git. Не запускайте публичный файловый сервер из корня репозитория: студия сама отдаёт только перечисленные файлы интерфейса.

## Восстановление доступа

С доступом к терминалу сервера:

```powershell
npm run setup -- --reset
```

Команда заменяет пароль настроенного владельца, завершает все его сеансы и удаляет все прежние passkeys. Ключи потребуется добавить заново. Это восстановление учётной записи, а не обычная смена пароля. Обычная смена пароля в интерфейсе оставляет текущий сеанс и passkeys, но завершает другие сеансы.

Нет публичной ссылки «Забыли пароль», SMTP или обходного HTTP-адреса первоначальной настройки. Создание владельца выполняется только локальной командой с доступом к приватной базе.

## Публикация

До запуска снаружи необходимо выбрать хостинг и постоянный адрес, например `https://studio.vitalykrauss.art`. DNS пока не изменялся.

1. Установить зависимости (`npm ci`) и собрать клиент (`npm run build`).
2. Создать приватный `.env`, пользуясь `.env.example`. Указать `BETTER_AUTH_URL` с окончательным HTTPS-адресом, `OWNER_EMAIL`, новый случайный `BETTER_AUTH_SECRET` и `NODE_ENV=production`.
3. Указать `AUTH_DATABASE_PATH` на постоянном приватном диске. Обеспечить доступ только пользователю процесса и настроить резервные копии SQLite. Папка базы не должна обслуживаться веб-сервером. На Windows доступ ограничивается ACL; Unix mode сам по себе ACL Windows не заменяет.
4. Выполнить `npm run setup` на сервере для создания владельца. Команда не перезаписывает существующий `.env`. Не использовать тестовую базу или тестовые пароли.
5. Настроить HTTPS-прокси, сохраняющий исходный `Host`. По умолчанию процесс слушает только `127.0.0.1:4174`. `HOST=0.0.0.0` нужен только для контролируемой контейнерной сети или аналогичного размещения.
6. Если используется прокси, задать `TRUST_PROXY_IPS` его точными IP-адресами. Прокси должен перезаписывать `X-Forwarded-For`, а прямой доступ к процессу должен быть закрыт. Не задавать доверие ко всем адресам. Для локального nginx это обычно `127.0.0.1,::1`. Без этой настройки доверяется только IP сокета, заголовки клиента игнорируются.
7. Запустить `npm start` под менеджером процессов, проверить вход, выход, passkey и резервное восстановление на окончательном домене. Не копировать локальные passkeys: они привязаны к домену.

Изменение `BETTER_AUTH_SECRET` завершает действующие входы. Изменение домена потребует повторной настройки ключей. Вход без TLS разрешён исключительно для локальной разработки; конфигурация production требует HTTPS.

## VPS с уже установленными сервисами

В `Dockerfile` и `compose.yaml` подготовлен отдельный контейнер. Он не занимает порты 80/443, не использует Docker socket, не меняет соседние контейнеры и хранит базу в собственном именованном томе. Привязка по умолчанию — только `127.0.0.1:4174` на хосте. Если порт уже занят, задайте свободный `STUDIO_BIND_PORT` в `.env`. Не запускайте второй экземпляр с тем же именем Compose-проекта, если он уже используется на этом сервере.

После проверки существующих портов, Docker-проектов и HTTPS-прокси:

1. Поместить `admin/` в отдельную папку, например `/opt/vitalykrauss-studio`.
2. Создать `.env` из `.env.example`. Указать окончательный HTTPS-домен, владельца, production и случайный секрет. Секрет можно получить локально командой `openssl rand -base64 48`; не пересылать его в чат и не добавлять в Git. Ограничить права файла: `chmod 600 .env`.
3. Выполнить `docker compose build`.
4. Создать владельца: `docker compose run --rm --no-deps studio npm run setup`. При полном окружении команда ничего не пишет в корень контейнера; сохраняет только хеш в приватном томе. Пароль запрашивается в терминале.
5. Выполнить `docker compose up -d`.
6. Добавить новый поддомен в существующий прокси, направив его на выбранный локальный порт. Не устанавливать второй nginx/Caddy поверх существующего и не заменять его общую конфигурацию.

Для nginx на хосте в новом HTTPS-виртуальном хосте потребуются, в частности:

```nginx
location / {
    proxy_pass http://127.0.0.1:4174;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto https;
    client_max_body_size 64k;
}
```

Сертификат и виртуальный хост подключаются средствами уже установленного прокси/панели. Если и прокси находится в Docker, сетевое подключение адаптируется к его существующей сети вместо публикации порта наружу. Точный `TRUST_PROXY_IPS` берётся из фактической сетевой конфигурации: при Docker это адрес прокси/шлюза, видимый контейнеру, а не обязательно `127.0.0.1`. Проверить разделение лимитов для двух внешних клиентов.

Не выполнять `docker compose down -v`: это удаляет том с владельцем, сессиями и passkeys. Для восстановления доступа использовать `docker compose run --rm --no-deps studio npm run setup -- --reset`. Контейнер работает без root и с файловой системой только для чтения; writable остаются приватный том и временная папка.

Docker-сборка и размещение проверены на VPS: контейнер работает без root, с файловой системой только для чтения и без опубликованных портов. Для существующего Docker-прокси используется `compose.vps.yaml` вместе с `compose.yaml`. Перед применением на другом сервере нужно создать отдельную сеть, подключить к ней прокси и указать его доверенный IP.

Лимиты входа хранятся в базе и разделяются по адресу клиента. Для внешнего сервера также нужны лимиты запросов и ограничение размера тела на HTTPS-прокси. SQLite рассчитана здесь на один процесс студии с постоянным диском, а не на независимые serverless-инстансы.

## Границы доступа

- Срок сеанса — 8 часов; изменение срока не кэшируется в клиентском токене. Чувствительные операции passkey требуют свежего входа по правилам Better Auth.
- Каждый приватный запрос повторно проверяет сессию и адрес подтверждённого владельца. Вход другого пользователя не создаёт сессию даже при наличии его записи в базе.
- Для запросов изменения обязателен точный Origin. Список доступных HTTP-методов и маршрутов авторизации ограничен сервером.
- Секреты, owner allowlist, хеши, сырые токены сессий и серверные ошибки не встраиваются в клиент. Доступен только минимальный профиль уже вошедшего владельца.
- Cookie: HttpOnly, SameSite=Lax, Secure для HTTPS, без передачи между поддоменами. Интерфейс запрещает встраивание и кэширование, отмечен noindex. Это дополнения к авторизации, а не замена ей.
- Нет исходящих писем и доступа к Gmail. Запросы покупателей пока обрабатываются публичным сайтом через `mailto:`.

## Проверки

```powershell
npm test
npm run check
npm run build
npm audit --omit=dev
```

Интеграционные тесты используют отдельные временные базы, реальные HTTP-запросы и Better Auth. Проверяются закрытая регистрация, владелец, сессии/выход/истечение, Origin/Host, Secure-cookie, лимиты и подделка IP-заголовков, защита passkey и файлов, восстановление.

Браузерная проверка в Edge с Playwright: 320/375/768/1440 px, ошибка пароля, вход и выход, регистрация виртуального WebAuthn-ключа, вход этим ключом, смена пароля и удаление ключа. На production проверены действительный HTTPS-сертификат, экран входа на desktop/mobile, вход и выход владельца, запрет чужого Origin и недоступность закрытых файлов. Владелец создан на сервере; начальный пароль хранится только в приватном root-файле. Физические Face ID/Windows Hello и Safari/Firefox не проверялись. Тестовые локальные учётные записи и базы удаляются после проверки.
